\chapter{Sprint 1}
\label{chap:sprint-1}

This chapter presents the realization of Sprint 1, the foundation every
later sprint builds on: turning an uploaded CV or TDR into structured,
extracted data end to end, proven with a working screen rather than just a
backend status update.

\section{Sprint Goal}

\begin{quote}
Upload a real CV/TDR and see it turned into structured, extracted data
end-to-end -- the foundation every later sprint builds on, proven with a
working (if rough) screen, not just a backend status update.
\end{quote}

Sprint 1 ran July 6--10, 2026, with 43 points committed -- deliberately
front-loaded, since it also had to prove the riskiest technical
integration of the whole project (multi-key LLM provider routing across
free-tier providers, since there is no paid API access) rather than only
low-complexity setup work.

\section{Analysis}

The sprint goal reduces to one user-facing flow: an HR or bid-management
user uploads a document (a candidate CV or a client TDR), and the system
returns structured, reviewable data instead of a wall of unstructured text.
Two actors interact with the system this sprint:

\begin{description}
  \item[HR / bid manager] uploads CVs to build the internal candidate pool,
    and uploads TDRs to see what a mission actually requires (positions,
    diplomas, years of experience, sector, deadline).
  \item[System (backend pipeline)] parses whatever file format arrives,
    extracts structured fields via an LLM, persists the result, and returns
    it for review.
\end{description}

Four use cases were in scope: \emph{Upload CV}, \emph{Upload TDR},
\emph{Preview extracted CV}, and \emph{Preview extracted TDR}. Matching a
CV against a TDR (ADQ's core value proposition) is explicitly out of scope
for Sprint 1 -- extraction has to be trustworthy before scoring on top of it
means anything, which is why the sprint goal is phrased around "structured
data," not "a ranked shortlist."

Two non-functional constraints shaped every design decision this sprint,
both already flagged during sprint planning: there is no budget for paid
LLM APIs, so the system has to survive on free-tier quotas across multiple
providers; and the source documents are real French-language administrative
text -- CVs with inconsistent date formats, TDRs running to hundreds of
pages of mostly irrelevant boilerplate. Both constraints turned out to
matter far more in practice than in the original estimate (see
Section~\ref{chap:sprint-1}'s Retrospective).

\section{Design}

\subsection{Use Case Diagram}

\begin{center}
\begin{tabular}{@{}p{3.5cm}p{9.5cm}@{}}
\toprule
Actor & Use cases \\
\midrule
HR / bid manager & Upload CV; Upload TDR; Preview extracted CV; Preview extracted TDR \\
\bottomrule
\end{tabular}
\end{center}

Both upload use cases share the same internal shape: \emph{parse file} $\to$
\emph{extract structured data} $\to$ \emph{persist} $\to$ \emph{return for
preview}, which is why they share one pipeline implementation
(\texttt{app/features/pipeline/nodes/extract.py}) rather than two parallel
ones.

\subsection{Class Diagram (key classes)}

Three groups of classes matter this sprint:

\begin{description}
  \item[Domain models] (\texttt{app/domain/cv.py}, \texttt{app/domain/tdr.py})
    -- \texttt{CandidateCV} (composed of \texttt{Education},
    \texttt{Certification}, \texttt{Experience}, \texttt{LanguageProficiency})
    and \texttt{TDR} (composed of \texttt{ExpertPosition},
    \texttt{LanguageRequirement}). These are the validated, structured
    output of the pipeline -- strict Pydantic models with field validators
    that coerce the messy date/text shapes an LLM actually produces
    (partial dates, French month names, the literal string \texttt{"null"})
    into real typed values, or fail loudly when a value genuinely can't be
    trusted.
  \item[ORM models] (\texttt{app/database/models.py}) -- \texttt{Candidate},
    \texttt{CV}, \texttt{TDRModel}, \texttt{ExpertPositionModel}, mapping
    the domain models onto the Postgres schema from ADQ-1.
  \item[LLM routing] (\texttt{app/common/llm/router.py}) -- \texttt{ModelRouter}
    owns one \texttt{KeyPool} per provider (Groq, Gemini) and resolves a
    provider- and tier-specific model name (extraction vs.\ reasoning) on
    every call, falling back to a local Ollama model once both pools are
    exhausted.
\end{description}

\subsection{Sequence: Upload $\to$ Extract $\to$ Persist}

\begin{enumerate}
  \item Client (dashboard) sends \texttt{POST /candidates/cv} (or
    \texttt{POST /tdrs}) with the raw file.
  \item \texttt{ingest} parses the file (PDF or DOCX) into raw text,
    raising a typed \texttt{DomainError} on a corrupt/unsupported file.
  \item For a TDR, the raw text is chunked, embedded (local Ollama,
    \texttt{nomic-embed-text}), and the chunks closest to a fixed
    "profils/qualifications/personnel requis" query -- boosted by a small
    keyword score for terms that only appear in a real requirements section
    -- are kept for extraction (Section~\ref{chap:sprint-1}, Testing,
    covers why this step needed rework mid-sprint).
  \item \texttt{ModelRouter} is called once per chunk (TDR) or once for the
    whole document (CV) with a Pydantic schema as the structured-output
    target, rotating across Groq keys, then Gemini keys, then Ollama, on
    any retryable failure (rate limit, quota exhaustion, or the provider
    rejecting the generated structured output).
  \item The wire-level extraction result is converted into the strict
    domain model (\texttt{CandidateCV} / \texttt{TDR}), where field
    validators do the final date/type coercion.
  \item The service layer persists the result (\texttt{Candidate}+\texttt{CV}
    or \texttt{TDRModel}+\texttt{ExpertPositionModel} rows, with an explicit
    \texttt{session.flush()} between parent and child inserts) and returns
    it to the client for the preview page.
\end{enumerate}

\subsection{ModelRouter: per-provider, per-tier model resolution}

The first router implementation resolved a single shared model name
(\texttt{LLM\_EXTRACTION\_MODEL}) regardless of which provider ended up
serving the call -- unworkable once actually exercised, since Groq, Gemini,
and Ollama don't share a model-naming scheme (\texttt{llama-3.1-8b-instant}
means nothing to Gemini or Ollama). The fix: six explicit settings
(\texttt{\{GROQ,GEMINI,OLLAMA\}\_\{EXTRACTION,REASONING\}\_MODEL}), and
\texttt{ModelRouter} resolves \texttt{(provider, tier)} to a model name
freshly on every attempt in the fallback chain, rather than reusing
whatever string the first provider was given.

\begin{lstlisting}[language=Python]
self._models: dict[tuple[str, str], str] = {
    ("groq", "extraction"): settings.groq_extraction_model,
    ("groq", "reasoning"): settings.groq_reasoning_model,
    ("gemini", "extraction"): settings.gemini_extraction_model,
    ("gemini", "reasoning"): settings.gemini_reasoning_model,
    ("ollama", "extraction"): settings.ollama_extraction_model,
    ("ollama", "reasoning"): settings.ollama_reasoning_model,
}
\end{lstlisting}

\subsection{Retry escalation, not blind retry}

A cheap extraction-tier model (\texttt{llama-3.1-8b-instant}) is
unreliable at emitting valid JSON for a nested schema -- confirmed
empirically failing 3/3 attempts on the same real CV. Retrying the same
model rarely helps; \texttt{\_invoke\_structured\_extraction}'s single
retry instead escalates to \texttt{invoke\_reasoning()}, a stronger model,
keeping the common case cheap while giving a hard case a real second
chance.

\section{Testing}

The unit test suite (73 tests by the end of the sprint) covers: key-pool
rotation and exhaustion-to-Ollama fallback, per-provider model resolution,
date/type coercion edge cases (partial dates, French dates, the literal
string \texttt{"null"}), CV and TDR structured extraction against both
synthetic and real fixtures, service-level persistence (including the
FK-ordering fix below), and CORS configuration. All of it runs against
fake routers/sessions -- deliberately, so CI needs no real credentials.

That mocked suite was fully green for most of the sprint and still missed
four real bugs that only a live call against the actual Groq API surfaced
once real API keys were populated: a provider-specific exception type not
in the caught-exceptions tuple; a \texttt{date}-typed field whose JSON
schema format Groq enforces server-side before any of the project's own
validation runs; the extraction-tier model's outright unreliability on a
nested schema; and a SQLAlchemy insert-ordering issue that only manifests
against a real Postgres, not a fake session. A second live pass -- this
time against all 3 real TDR samples rather than only the synthetic CVs --
surfaced three more: literal-string \texttt{"null"} values, non-ISO
(French-written) dates, and a chunk-retrieval failure on a 268-page TDR
whose unrelated annexes out-scored the actual staffing section on pure
embedding similarity. Every one of these is now a permanent regression
test, and the lesson is recorded for future sprints: a green mocked suite
proves the code's logic is internally consistent, not that its contract
with an external system holds.

Intentionally not covered this sprint: true end-to-end integration tests
that hit a live Groq/Gemini/Ollama endpoint as part of the automated suite
(no committed API keys, by design), and any accuracy metric beyond manual
spot-checking -- that's ADQ-8's gold-set annotation work, still ongoing.

\section{Sprint Review}

The sprint was demoed against its own goal: a synthetic CV and a real TDR
were uploaded through the running dashboard pages, and the extracted
fields (candidate education/experience/certifications; TDR mission
metadata and expert positions with diploma/experience requirements)
rendered correctly on the preview screen. All 6 synthetic CVs and all 3
real TDRs were verified end-to-end against live Groq/Gemini/Ollama calls,
across multiple repeated runs, by the end of the sprint -- not just once.

\section{Sprint Retrospective}

\textbf{What worked:} tackling the multi-provider LLM routing risk first,
as flagged in sprint planning, paid off -- every bug it surfaced (provider
error handling, model-name resolution, retry strategy) was found and fixed
before it could block later sprints' work on top of it. Building the
gitignored synthetic CV fixtures early (ADQ-4/ADQ-3) meant extraction work
never had to wait on real data that, per ADQ-9, never actually arrived.

\textbf{What didn't:} the original 43-point estimate assumed a single pass
of "wire the LLM call, validate the schema" would be enough. In practice,
real documents needed two full rounds of live testing to actually trust --
the mocked test suite's green checkmarks were necessary but not
sufficient, and each round surfaced problems (provider-specific exception
types, server-side schema enforcement, chunk-retrieval quality on long
documents) that were only visible against real input, real APIs, and a
real quota ceiling. Sprint planning should budget for this explicitly next
time: "extraction works on the happy path" and "extraction survives real
documents and free-tier rate limits" are different milestones, and this
sprint's estimate only accounted for the first one.

\textbf{Change for Sprint 2:} keep at least one round of live
verification against real documents inside the sprint's own time budget,
not as a stretch goal -- it is where most of this sprint's real bugs were
actually found.

\section{Conclusion}

Sprint 1 delivered a working, live-verified upload-to-extraction pipeline
for both CVs and TDRs, with a multi-provider LLM routing layer robust
enough to survive free-tier rate limits, quota exhaustion, and unreliable
structured-output generation -- the foundation the matching and scoring
work in later sprints depends on. The two open items (ADQ-8's gold-set
annotation and ADQ-9's company data request) carry forward, the latter now
tracked as a set of explicit, revisable working assumptions rather than a
silent blocker.
