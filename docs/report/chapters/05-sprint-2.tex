\chapter{Sprint 2}
\label{chap:sprint-2}

This chapter presents the realization of Sprint 2, which turns Sprint 1's
trustworthy extraction pipeline into the project's actual value
proposition: given a TDR position and the candidate pool, produce a real
ranked shortlist with sub-scores, visible in a working matching results
view -- and, once that was demonstrably working, use live testing against
it to find and fix real defects rather than declaring victory on green
tests alone.

\section{Sprint Goal}

\begin{quote}
Given a TDR position and the CV pool, produce a real ranked shortlist
with sub-scores -- visible in a working matching results view.
\end{quote}

Sprint 2 ran July 13--17, 2026, with 42 points committed. Unlike Sprint 1
(which had to prove a single high-risk integration), this sprint's risk
was distributed across a genuine pipeline of five sequential stages
(coarse retrieval, skill normalization, hard filtering, soft scoring,
persistence/render), each depending on the last -- correctness had to
hold at every stage for the ranked list at the end to mean anything.

\section{Analysis}

The sprint goal reduces to one new user-facing flow on top of Sprint 1's
upload screens: given an already-extracted TDR, produce and display a
ranked list of candidates per expert position. Two actors, extending
Sprint 1's:

\begin{description}
  \item[HR / bid manager] clicks \emph{Run matching} on an extracted TDR,
    then reviews the ranked shortlist per position -- compatibility
    score, pass/fail hard-filter status with a reason, and skill/sector
    sub-scores.
  \item[System (matching pipeline)] shortlists plausible candidates
    cheaply before doing any expensive per-candidate work, normalizes
    both the position's and each candidate's raw skill strings against a
    shared taxonomy, applies hard eligibility filters, computes weighted
    soft scores for whoever's left, and persists + serves the ranked
    result.
\end{description}

One use case was in scope: \emph{Run Matching for a TDR}, decomposing
into \emph{View Ranked Shortlist} per position once results land. Report
generation with cited rationale, anomaly detection, and human-in-the-loop
review/override are explicitly out of scope -- those need the LLM
reasoning layer deferred to Sprint 3.

The central non-functional constraint this sprint: matching has to stay
cheap enough to run against the whole CV pool per TDR position without
either an LLM call or an unindexed full-table scan being the bottleneck.
This shaped the two-phase architecture described in
Section~\ref{chap:sprint-2} (Design) -- a cheap embedding-only coarse
filter runs before any of the more expensive per-candidate normalization
or scoring work.

\section{Design}

\subsection{Use Case Diagram}

\emph{Run Matching} requires a TDR whose extraction has already completed
(\texttt{status = "done"}) -- attempting it earlier is rejected with a 409
by \texttt{TdrsService.run\_matching}, reusing the same
\texttt{ResourceNotReadyError} pattern Sprint 1 established for
in-progress extractions.

\subsection{Class Diagram (key classes)}

Four groups of classes matter this sprint:

\begin{description}
  \item[Domain models] (\texttt{app/domain/matching.py}) --
    \texttt{NormalizedSkill} (a raw term matched, or not, to a taxonomy
    canonical id, with a confidence and a \texttt{matched\_via} label),
    \texttt{SubScores} (skill/sector this sprint; education/experience/
    certification/language stay \texttt{null} until Sprint 3's LLM
    judgment context exists), and \texttt{MatchResult} (hard-filter
    outcome, failure reasons, compatibility score, sub-scores).
  \item[ORM models] (\texttt{app/database/models.py}) --
    \texttt{SkillTaxonomy} (canonical term + aliases + embedding) and
    \texttt{MatchResult}, the persisted counterpart of the domain model
    above.
  \item[Coarse retrieval] (\texttt{app/features/matching/coarse\_retrieval.py})
    -- \texttt{shortlist\_candidates}, a pgvector cosine search over
    \texttt{cvs.embedding} re-ranked with sector-overlap and
    years-proximity boosts, zero LLM calls.
  \item[Pipeline nodes] (\texttt{app/features/pipeline/nodes/\{normalize\_skills,score\}.py})
    -- \texttt{normalize\_position\_skills}/\texttt{normalize\_cv\_skills}
    (retrieve $\to$ rerank $\to$ retry-once against the taxonomy),
    \texttt{check\_hard\_filters}, \texttt{score\_soft\_criteria}.
\end{description}

\subsection{Sequence: Run Matching}

\begin{enumerate}
  \item Client sends \texttt{POST /tdrs/\{id\}/match}; the request
    returns immediately (202) and the run proceeds on the same RQ worker
    pattern Sprint 1 established for extraction
    (\texttt{app/worker/matching\_tasks.py}).
  \item For each expert position on the TDR: \texttt{shortlist\_candidates}
    runs coarse retrieval once (top $\sim$30 by cosine similarity,
    re-ranked by sector/years boost, final shortlist $\sim$10).
  \item The position's own required skills are normalized against the
    taxonomy \emph{once} (\texttt{normalize\_position\_skills}) and its
    required-sector text embedded \emph{once} -- both are
    candidate-independent, computed before the per-candidate loop, not
    inside it.
  \item For each shortlisted candidate: their raw skills are normalized
    against the taxonomy, \texttt{check\_hard\_filters} evaluates
    diploma/years/certifications, and \texttt{score\_soft\_criteria}
    computes skill/sector sub-scores and a weighted compatibility score.
  \item Old \texttt{match\_results} rows for that position are deleted
    and the fresh set inserted in the same transaction -- reruns are
    idempotent.
  \item The frontend polls \texttt{GET /tdrs/\{id\}/match-status}, then
    fetches \texttt{GET /positions/\{id\}/matches} per position once done,
    rendering a ranked table with compatibility \%, a pass/fail badge
    (hover or keyboard-focus for the failure reason), and skill/sector
    sub-score bars.
\end{enumerate}

\section{Implementation}

\subsection{ADQ-10: Skill/certification taxonomy}

\texttt{backend/app/features/pipeline/seed\_data/skill\_taxonomy.json} +
\texttt{backend/scripts/seed\_skill\_taxonomy.py} (idempotent, upserts by
canonical name). Started at 70 hand-curated terms against the Sprint 1
sample data; grown to 104 later in the sprint (Section~\ref{chap:sprint-2},
Data ownership) by mining vocabulary directly out of a much larger real
TDR sample.

\subsection{ADQ-11: Coarse retrieval}

\begin{lstlisting}[language=Python]
similarity = cosine(position_embedding, cv_embedding)
    + sector_boost  # +0.15 if any CV experience.sector overlaps
    + years_boost   # +0..0.15 scaled by years over minimum, -0.15 if under
\end{lstlisting}

The years boost never \emph{excludes} anyone -- it only ranks
comfortably-qualified candidates a bit higher within the shortlist. ADQ-15's
hard filter is what actually rejects under-experienced candidates, later
in the pipeline, where the rejection reason can be surfaced to the
reviewer rather than silently dropping someone from the shortlist.

\subsection{ADQ-12--14: \texttt{normalize\_skills}}

Turning a raw skill string into a taxonomy match, in up to two tries:
embed the term, pgvector top-5 against \texttt{skill\_taxonomy}, apply a
+0.15 exact-match-on-alias bonus, accept if similarity $\geq 0.75$
(\texttt{matched\_via = "direct"}). Below threshold, look the term up in a
curated FR/EN + abbreviation map, re-embed, retry once
(\texttt{matched\_via = "rag\_retry"} if that wins). Still unresolved:
\texttt{canonical\_id = null}, confidence kept for visibility rather than
silently discarded. No LLM fallback tier this sprint -- that path, and
\texttt{score}'s LLM judgment generally, is Sprint 3.

\subsection{ADQ-15--16: \texttt{score}}

Hard filters (pass/fail, no partial credit): diploma (a parsed
"Bac+$N$" mapped to degree-level keywords, or a keyword-overlap fallback
for free-text diplomas), minimum years, and required certifications
(substring match, not expired). Soft sub-scores, only skill and sector
this sprint:

\begin{lstlisting}[language=Python]
skill_score = |required skills matched among candidate's skills|
              / |required skills|
sector_score = max(cosine(required_sector, sector)
                    for sector in candidate.experience_sectors)
compatibility_score = 0.6 * skill_score + 0.4 * sector_score
\end{lstlisting}

Fixed 0.6/0.4 weights, not yet per-TDR configurable --
\texttt{ExpertPosition.evaluation\_weight} is a single scalar today, not
something that splits meaningfully across two criteria yet.

\subsection{ADQ-17: Matching results view -- the demoable slice}

Built inline into the existing \texttt{/tdrs} page rather than a new
route: a \emph{Run matching} button appears once a TDR finishes
extracting, and each position gets its own ranked table once results
land -- candidate name, compatibility \%, a Passed/Failed badge (hover or
keyboard-\texttt{Tab} for the failure reason), and skill/sector sub-score
bars.

\subsection{ADQ-18: Retrieval metrics}

\texttt{backend/tests/eval/fixtures/matching/gold\_matching\_set.json} +
\texttt{test\_matching\_retrieval\_quality.py}, run explicitly via
\texttt{uv run pytest -m eval} (hits real embeddings, needs the real CV
pool seeded). Initial result at 6 hand-crafted entries: Recall@3 = 1.0,
Precision@3 = 0.33 (expected, with only one truly relevant candidate per
position against a $k=3$ shortlist). Grown later in the sprint to 11
entries (Section~\ref{chap:sprint-2}, Data ownership); the same result
held at the larger, more varied scale.

\subsection{Final verification round: TDR reprocessing and matching state management}

Once the matching view was demoable and exercisable end-to-end, a second round of
thorough manual testing against a real TDR (UNFPA Egypt's \emph{TOR-Software
Developer.pdf}, four expert positions: Software Developer, Developer, Consultant,
Web Developer) surfaced two additional defects in components that had passed
mocked tests:

\begin{enumerate}
  \item \textbf{TDR reprocessing accumulated stale positions indefinitely.}
    A user running \texttt{force=true} re-upload on an already-processed TDR to apply
    a pipeline fix would trigger a fresh extraction and re-insert of all expert
    positions, but \texttt{run\_tdr\_extraction\_job} never deleted the stale
    \texttt{ExpertPosition} rows from the prior run. A test TDR ballooned from its
    real 4 positions to 15, then 19, on successive force-reprocesses because every
    fresh extraction appended instead of replaced. Fixed by deleting both
    \texttt{MatchResult} rows (which reference the positions via FK) and
    \texttt{ExpertPosition} rows for that \texttt{tdr\_id} immediately before the
    insert loop, in FK-safe order. Verified live by force-reuploading an already-
    processed TDR and confirming the position count reverted to the correct number.

  \item \textbf{Matching job enqueue did not reset stale Redis progress state.}
    \texttt{TdrsService.run\_matching} enqueued the RQ matching job without first
    resetting the Redis progress key (\texttt{tdr:\{id\}:matching\_progress}). A
    frontend poll landing in the gap between the API's 202 response and the RQ
    worker actually dequeuing could read stale status (e.g.\ ``done'') left over
    from a \emph{previous} matching run on the same \texttt{tdr\_id}, causing the UI
    to stop polling and fetch (non-existent) match results before the new run had
    actually scored anything. The user saw ``No shortlisted candidates for this
    position'' for every position, even though matching completed moments later with
    real results. Fixed by synchronously writing \texttt{status=``processing''},
    \texttt{positions\_done=0}, \texttt{positions\_total=0} to Redis before
    enqueueing, so any poll in the gap reads a non-terminal state and keeps waiting.
    Verified live by running matching twice in succession on the same TDR and
    confirming the second run's results replaced the first with fresh data, no stale
    state leakage.
\end{enumerate}

Both bugs were found via live manual testing against a real TDR PDF uploaded through
the actual running app — not mocked HTTP clients, not synthetic test data, but the
exact end-to-end path an HR user would take. This is consistent with Sprint 1's
retrospective lesson: a green mocked test suite is necessary but not sufficient;
real input against a real stack catches defects that pure unit testing misses.

\subsection{Hardening pass: a second, meticulous review}

Once ADQ-10 through ADQ-18 were demoable, every file changed since
Sprint 1's close-out was read directly (not delegated to a summarizing
pass) end to end for correctness, transaction/error-handling soundness,
N+1 query patterns, data leakage, and convention adherence. Twelve real
findings came out of it and all twelve were fixed, not just the five
initially proposed -- among them: typed \texttt{UUID} path parameters
(replacing manual \texttt{UUID(...)} parsing that surfaced a malformed id
as a raw 500 instead of a clean 422), hoisting position-scoped
normalization/embedding work out of the per-candidate scoring loop (a
position with 3 required skills and a 10-candidate shortlist was
re-querying the taxonomy 30 times instead of 3), an ivfflat index
\texttt{lists} retune (the pgvector default of 100 lists against a
few dozen rows meant most lists held zero or one row -- a true nearest
neighbor could land in a list that never gets probed, silently degrading
retrieval with no error), and an accessibility fix (the results table's
info tooltip trigger was a bare, unfocusable SVG icon, unreachable by
keyboard). Every fix was verified against the live running stack, not
just re-run through the mocked test suite.

\subsection{Data ownership: growing the pool and the taxonomy ourselves}

The company never responded to the Sprint 1 data request
(\texttt{docs/08-company-data-checklist.md}) -- rather than treat the
6-candidate, 3-TDR pool as a permanent ceiling, the team sourced 10 more
real TDR documents (spanning AI/RAG knowledge hubs, AI chatbot
prototypes, secure web development, .NET/C\# enterprise systems, and
mobile + conversational-AI apps, across several real donors/clients --
AfDB, ILO, World Bank GovTech, among others) and mined their actual
requirement text directly, growing the skill taxonomy from 70 to 104
terms with real vocabulary (\texttt{Retrieval-Augmented Generation},
\texttt{OWASP}, \texttt{SSO}, \texttt{ASP.NET MVC}, \texttt{Design
Patterns}, \texttt{GitLab CI/CD}, and more) rather than guessed terms.
Five new synthetic candidate personas were designed specifically to close
the skill/domain gaps that larger, more varied sample exposed -- an
AI/RAG engineer, a mobile + conversational-AI developer, a cybersecurity
specialist, a .NET/C\# enterprise developer, and a software architect --
growing the candidate pool from 6 to 11, each with a real-sounding,
correctly-extracted certification.

The gold matching set (ADQ-18) was expanded the same way and explicitly
reframed: rather than a stopgap standing in for real historical staffing
decisions that were never going to arrive, it is treated as the project's
actual working ground truth, deliberately grown alongside the pool -- 11
entries, one per candidate, ten hand-crafted with the same rigor a real
labeling pass would need and one (\texttt{gold-software-developer-ilo-real})
pulled verbatim from a genuinely real TDR extraction rather than
invented, to keep the set honest about what production extractions
actually look like.

\subsection{Live-testing-driven fixes}

Continuing Sprint 1's retrospective lesson -- that a green mocked suite
proves internal consistency, not a contract with the real system -- the
newly-demoable matching view was exercised live against a real TDR (an
AfDB "AI Chatbot" position) once it existed, and that live run
immediately surfaced two real defects no unit test had caught:

\begin{enumerate}
  \item \textbf{TDR skill extraction returning full sentences, and a
    cross-chunk merge bug.} \texttt{required\_skills} entries were
    coming back as entire clauses (\emph{"design, develop, and implement
    AI-driven chatbots"}) instead of atomic terms, which never embeds
    close enough to any taxonomy entry -- \texttt{skill\_score} came back
    \texttt{0.0} even for genuinely relevant candidates. Fixing the
    extraction guardrail prompt (explicit atomic-term instruction with
    few-shot examples) exposed a second, more fundamental bug while
    verifying the fix live: \texttt{extract\_tdr}'s chunk-merge step
    deduplicated positions by title and kept only the \emph{first}
    chunk's extraction of a given position, silently discarding every
    other chunk's contribution to that same position. A short TDR
    describing one role across several chunks (context in one chunk, the
    skills bullet list in another, education/years in a third) lost
    everything but whichever chunk was processed first. Fixed by merging
    same-titled positions' fields (union of skills/certifications/
    languages, first non-null diploma/years/sector) instead of
    discarding. Verified live against a real ILO TDR: before the fix, one
    skill and no diploma/years survived merge; after, 35 atomic skills,
    the correct diploma, and the correct minimum years all merged
    correctly.
  \item \textbf{Hard-filter failures hid all scoring signal.} Soft
    sub-scores were only computed when a candidate passed the hard
    filter -- a candidate who was the best skill match but missed on
    years showed nothing but a bare failure string, no way to tell
    "great fit, just short on years" from "irrelevant and short on
    years." Fixed by computing sub-scores unconditionally while keeping
    \texttt{compatibility\_score} (the ranking number) gated on
    \texttt{hard\_filter\_passed} -- a rejected candidate is still never
    \emph{ranked}, but their fit is now visible. No frontend change was
    needed; the results table already rendered sub-scores conditionally
    on their presence.
\end{enumerate}

A third, related gap was closed proactively rather than found live: every
CV/TDR upload created a new row unconditionally, and TDR uploads always
re-ran the full LLM extraction pipeline even for a file already known.
Migration \texttt{0006} adds a nullable, unique-indexed
\texttt{content\_hash} column to both \texttt{cvs} and \texttt{tdrs};
both upload paths now hash the incoming file and short-circuit to the
existing record on a match -- verified live by re-uploading an
already-processed TDR and confirming no new row was created and no new
extraction job was enqueued.

The dedup guard raised an immediate follow-up question: once a file is
hashed and cached, does a pipeline bug fix (like the two above) ever
reach a document uploaded \emph{before} the fix? Without an escape hatch,
no -- the cached extraction would be served forever. Both
\texttt{POST /tdrs} and \texttt{POST /candidates/cv} now accept an
optional \texttt{force=true} query parameter: on a hash hit, instead of
returning the cached record, it resets the same row (same
\texttt{tdr\_id}/\texttt{candidate\_id}, same \texttt{content\_hash} --
required, since the column is unique-indexed) to re-run extraction
against current code and overwrite the stored result in place. This is
an explicit, user-triggered action, not automatic re-processing on every
deploy -- growing the CV/TDR pool or shipping an unrelated fix does not
retroactively touch already-processed documents; only a deliberate
\texttt{force=true} re-upload of a specific file does.

\section{Testing}

The backend unit suite grew to 125 tests by the end of the sprint,
covering coarse retrieval, taxonomy matching (direct/retry/unresolved
paths), hard-filter edge cases (diploma parsing, expired certifications),
sub-score computation, and the upload-dedup paths (a miss that proceeds
normally, a hit that returns the existing record without re-extracting,
and a \texttt{force=true} hit that re-extracts in place onto the same
row). All of it runs against fake routers/sessions, same as Sprint 1.

The retrieval-quality eval (\texttt{uv run pytest -m eval}) and the live
API/worker stack were both exercised repeatedly against real running
services, not just the mocked suite -- this sprint's real bugs (both
described above) were only found this way, consistent with Sprint 1's
retrospective finding. One operational lesson surfaced during this
process worth recording: \texttt{docker compose restart} does not pick up
source changes for services built from an image (\texttt{build: ./backend}
with no source bind mount) -- a code fix can silently keep running the
pre-fix container unless \texttt{docker compose up -d --build} rebuilds
the image first. Several live "verifications" had to be re-run once this
was caught.

\section{Sprint Retrospective}

\textbf{What worked:} the two-phase architecture (cheap coarse retrieval
before any expensive per-candidate work) held up under real load without
rework, and the decision to hoist position-scoped normalization/embedding
work out of the per-candidate loop during the hardening pass -- rather
than deferring it as a "nice to have" -- turned a real
$O(\text{positions} \times \text{candidates})$ cost into
$O(\text{positions} + \text{candidates})$ before it became a problem at a
larger candidate pool.

\textbf{What didn't:} the sprint's own live-testing lesson from Sprint 1
was under-applied at first -- ADQ-10 through ADQ-18 shipped and passed
their mocked tests before a single real TDR was run all the way through
the finished matching view. Both real defects (extraction atomicity/merge,
hidden sub-scores) were sitting in code that had been "done" for some
time before live testing surfaced them. The docker-image staleness issue
compounded this: a code fix was verified "live" twice against a
container that hadn't actually rebuilt, producing a false negative that
took real time to diagnose.

\textbf{Change for Sprint 3:} treat "demoable" and "live-tested against a
real document end to end, through a freshly rebuilt stack" as two
separate gates, not one -- the first isn't sufficient evidence for the
second, and this sprint paid for conflating them.

\section{Conclusion}

Sprint 2 delivered a real, ranked, sub-scored matching pipeline running
end to end with zero LLM calls, backed by a 104-term taxonomy and an
11-candidate pool the team grew and owns itself rather than waiting on
data that was never going to arrive. Beyond the committed backlog: a
twelve-finding hardening pass fixed real correctness and efficiency
issues before they could compound in Sprint 3, and two rounds of live
testing against real TDRs found and fixed four defects no mocked test had
caught: an extraction-merge data-loss bug, a scoring-visibility gap, TDR
reprocessing accumulating stale positions indefinitely, and matching job
enqueue not resetting stale Redis progress state. Additionally, a proactive
upload-deduplication guard with an explicit \texttt{force=true} escape hatch
was added to prevent pipeline bugs from being permanently masked by file
caching. The retrieval-quality eval (Recall@3 = 1.0, Precision@3 = 0.33 across
11 varied positions) and the newly-honest gold matching set give Sprint 3's
LLM-judgment and human-in-the-loop work a real, growing foundation to build
on rather than a synthetic placeholder.
