\chapter{Sprint 1 --- Ingestion and Structured Extraction}
\chaptermark{Sprint 1 --- Ingestion \& Extraction}
\label{chap:sprint-1}

This chapter presents the realization of Sprint 1: turning an uploaded CV
or TDR into structured, extracted data end to end, covering the sprint's
backlog, design, implementation, testing, and review.

\section{Sprint Goal}

\begin{quote}
Upload a real CV/TDR and see it turned into structured, extracted data
end-to-end: the foundation every later sprint builds on, proven with a
working screen, not just a backend status update.
\end{quote}

Sprint 1 ran July 6--10, 2026, with 43 points committed, deliberately
front-loaded since it also had to prove the riskiest technical
integration of the whole project (multi-key LLM provider routing across
free-tier providers, since there is no paid API access) rather than only
low-complexity setup work.

ADQ-9's information request was answered in part: the company did provide
real TDR documents to work from, after real persistence chasing them down,
and those documents are the real samples used throughout this chapter and
the next. Historical staffing decisions, the single highest-value item on
the request, went unanswered through the end of the sprint. That gap was
resolved to an explicit, documented working assumption (grounded in the
real TDR samples in hand and in standard practice for a firm of this
kind), revisable the moment the company responds. The highest-risk open
assumption: whether cloud LLM APIs (Groq, Gemini) are acceptable for real
candidate data, or whether processing must stay fully local. The
architecture was built so that answer is a configuration change (disable
the two cloud providers in \texttt{ModelRouter}, run against Ollama only)
rather than a redesign, precisely because it couldn't be confirmed in time.

\section{Analysis}

The sprint goal decomposes into one user-facing flow: an HR or bid-management
user uploads a document (a candidate CV or a client TDR), and the system
returns structured, reviewable data instead of a wall of unstructured text.
One actor interacts with the system this sprint:

\begin{description}
  \item[HR / bid manager] uploads CVs to build the internal candidate pool,
    and uploads TDRs to see what a mission actually requires (positions,
    diplomas, years of experience, sector, deadline).
\end{description}

The system itself parses whatever file format arrives, extracts
structured fields via an LLM, persists the result, and returns it for
review.

Four use cases were in scope: \emph{Upload CV}, \emph{Upload TDR},
\emph{Preview extracted CV}, and \emph{Preview extracted TDR}. Matching a
CV against a TDR (ADQ's core value proposition) is explicitly out of
scope for Sprint 1: extraction has to be trustworthy before scoring on
top of it means anything.

Two non-functional constraints shaped every design decision this sprint,
both already flagged during sprint planning: there is no budget for paid
LLM APIs, so the system has to survive on free-tier quotas across multiple
providers, and the source documents are real French-language administrative
text: CVs with inconsistent date formats, TDRs running to hundreds of
pages of mostly irrelevant boilerplate. Both constraints mattered far more
in practice than in the original estimate (see the Retrospective,
Section~\ref{sec:s1-retro}).

\subsection{Class Diagram (key classes)}

Figure~\ref{fig:s1-class} shows the sprint's key classes, in three groups.
The domain models (\texttt{app/domain/\{cv,tdr\}.py})
are the validated, structured output of the pipeline: strict Pydantic
models with field validators that coerce the messy date/text shapes an
LLM actually produces (partial dates, French month names, the literal
string \texttt{"null"}) into real typed values, or fail loudly when a
value genuinely can't be trusted. The ORM models
(\texttt{app/database/models.py}) map these onto the Postgres schema
from ADQ-1. \texttt{ModelRouter} (\texttt{app/common/llm/router.py})
owns one \texttt{KeyPool} per provider (Groq, Gemini) and resolves a
provider- and tier-specific model name (extraction vs.\ reasoning) on
every call, falling back to a local Ollama model once both pools are
exhausted.

\subsection{ModelRouter: per-provider, per-tier model resolution}

An early design assumed a single shared model name
(\texttt{LLM\_EXTRACTION\_MODEL}) would work regardless of which provider
served the call. Testing it against Groq, Gemini, and Ollama quickly
surfaced the real constraint before it reached any other code: the three
providers don't share a model-naming scheme
(\texttt{llama-3.1-8b-instant} means nothing to Gemini or Ollama). The
design was adjusted accordingly: six explicit settings
(\texttt{\{GROQ,GEMINI,OLLAMA\}\_\{EXTRACTION,REASONING\}\_MODEL}), and
\texttt{ModelRouter} resolves \texttt{(provider, tier)} to a model name
freshly on every attempt in the fallback chain, rather than reusing
whatever string the first provider was given.

\begin{lstlisting}[language=Python]
self._models: dict[tuple[str, str], str] = {
    ("groq", "extraction"): settings.groq_extraction_model,
    ("groq", "reasoning"): settings.groq_reasoning_model,
    ("gemini", "extraction"): settings.gemini_extraction_model,
    ("gemini", "reasoning"): settings.gemini_reasoning_model,
    ("ollama", "extraction"): settings.ollama_extraction_model,
    ("ollama", "reasoning"): settings.ollama_reasoning_model }
\end{lstlisting}

\subsection{Retry escalation, not blind retry}

A cheap extraction-tier model (\texttt{llama-3.1-8b-instant}) is
unreliable at emitting valid JSON for a nested schema, confirmed
empirically by 3/3 failed attempts on the same real CV. Retrying the same
model rarely helps; \texttt{\_invoke\_structured\_extraction}'s single
retry instead escalates to \texttt{invoke\_reasoning()}, a stronger model,
keeping the common case cheap while giving a hard case a real second
chance.

\subsection{Asynchronous TDR Processing}

A real multi-section TDR (up to 268 pages) takes well over a minute to
process: every retained chunk is extracted by a separate LLM call, and a
call can itself retry-escalate to the slower reasoning-tier model. Holding
an HTTP request open for that long is not viable, and a silent
\texttt{"Uploading..."} spinner for a minute-plus is indistinguishable from
a hang from the user's side. \texttt{POST /tdrs} was reworked to return
immediately (status \texttt{processing}) after creating a placeholder row
and enqueueing the extraction job on an RQ worker
(\texttt{app/worker/tasks.py}), backed by Redis. The worker reports its
current stage (parsing, retrieving, extracting section $N$ of $M$, merging)
to a short-lived Redis hash as it progresses; a new
\texttt{GET /tdrs/\{id\}/status} endpoint reads it, and the dashboard polls
that endpoint every 1.5 seconds, replacing the static spinner with live
stage text until the row's status flips to \texttt{done} or \texttt{failed}.

\subsection{Extraction Quality Evaluation Harness}

Manually pasting an extraction result next to the source document and
eyeballing it does not scale, and does not protect a document that was
already fixed from silently regressing when a later change tunes retrieval
or the extraction prompt for a different document. \texttt{backend/tests/eval/}
formalizes this into a repeatable regression suite: each real sample TDR
gets a hand-verified fixture (the expected expert positions, diplomas, and
minimum years of experience, read once from the real document), and a
parametrized test runs the actual extraction pipeline against real
Groq/Gemini/Ollama calls and checks every fixture, printing an
expected-vs-actual table on any mismatch. It is deliberately excluded from
the default \texttt{pytest} run (real API quota, real wall-clock time) and
run explicitly via \texttt{uv run pytest -m eval}. Going forward, improving
extraction quality means finding a wrong extraction, adding or correcting
its fixture, tuning the pipeline, and re-running the full suite. Every
previously-fixed document is re-checked automatically, not just the one
currently being looked at.

\subsection{Frontend: Upload UX and Visual Identity}

The upload flow was hardened past the happy path: a shared
\texttt{FileUpload} component (built on shadcn's \texttt{@reui} file-upload
primitive) restricts both the CV and TDR upload forms to a single file,
and now surfaces an explicit message if a user drags multiple files onto
the drop zone instead of silently keeping only the first. Separately, the
dashboard's visual identity was finalized: a light/dark toggle (persisted
via \texttt{next-themes}, with a keyboard shortcut) replaced a fixed
dark-only palette, built on Tailwind v4's native \texttt{oklch()} color
support.

\section{Testing}
\label{sec:s1-testing}

The unit test suite (73 tests by the end of the sprint) covers: key-pool
rotation and exhaustion-to-Ollama fallback, per-provider model resolution,
date/type coercion edge cases (partial dates, French dates, the literal
string \texttt{"null"}), CV and TDR structured extraction against both
synthetic and real fixtures, service-level persistence (including the
FK-ordering fix below), and CORS configuration. All of it runs against
fake routers and sessions by design, so CI needs no real credentials.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.75\textwidth]{unit-tests-sprint1.png}
  \caption[Sprint 1 unit test run]{Full unit test run on the Sprint 1 branch: all 73 tests
  passing.}
  \label{fig:s1-unit-tests}
\end{figure}

That mocked suite was fully green for most of the sprint and still missed
four real bugs that only a live call against the actual Groq API surfaced
once real API keys were populated: a provider-specific exception type not
in the caught-exceptions tuple; a \texttt{date}-typed field whose JSON
schema format Groq enforces server-side before any of the project's own
validation runs; the extraction-tier model's outright unreliability on a
nested schema; and a SQLAlchemy insert-ordering issue that only manifests
against a real Postgres, not a fake session. A second live pass (this
time against all 3 real TDR samples rather than only the synthetic CVs)
surfaced three more: literal-string \texttt{"null"} values, non-ISO
(French-written) dates, and a chunk-retrieval failure on a 268-page TDR
whose unrelated annexes out-scored the actual staffing section on pure
embedding similarity. Every one of these is now a permanent regression
test. The lesson for future sprints: a green mocked suite proves the
code's logic is internally consistent, not that its contract with an
external system holds.

Intentionally not covered this sprint: true end-to-end integration tests
that hit a live Groq/Gemini/Ollama endpoint as part of the automated suite
(no committed API keys, by design). That role is filled by the
extraction-quality eval harness described above, run on demand rather than
on every commit.

Beyond automated tests, a full multi-angle code review pass was run
against every change this sprint (line-by-line correctness, removed
behavior, cross-file consistency, reuse, simplification, efficiency, and
convention adherence), plus \texttt{ruff}/\texttt{mypy} on the backend and
\texttt{eslint}/\texttt{tsc} on the frontend as a standing quality gate. It
surfaced five real correctness issues, carried forward for pickup in
Sprint 2 rather than fixed under this sprint's own time pressure, flagged
here rather than only in an internal note: finding a problem before it
reaches production is the point of this review, not something to omit
for looking cleaner on paper.

\section{Sprint Retrospective}
\label{sec:s1-retro}

\textbf{What worked:} tackling the multi-provider LLM routing risk first,
as flagged in sprint planning, paid off. Every bug it surfaced (provider
error handling, model-name resolution, retry strategy) was found and fixed
before it could block later sprints' work on top of it. Building the
gitignored synthetic CV fixtures early (ADQ-4/ADQ-3) meant extraction work
never had to wait on the real employee CVs that, per ADQ-9, never
actually arrived.

\textbf{What didn't:} the original 43-point estimate assumed a single pass
of "wire the LLM call, validate the schema" would be enough. In practice,
real documents needed two full rounds of live testing to earn trust: the
mocked test suite's green checkmarks were necessary but not sufficient,
and each round surfaced problems (provider-specific exception types,
server-side schema enforcement, chunk-retrieval quality on long documents)
that were only visible against real input, real APIs, and a real quota
ceiling. Sprint planning should budget for this explicitly next time:
"extraction works on the happy path" and "extraction survives real
documents and free-tier rate limits" are different milestones, and this
sprint's estimate only accounted for the first one.

\textbf{Change for Sprint 2:} keep at least one round of live
verification against real documents inside the sprint's own time budget,
not as a stretch goal. It is where most of this sprint's real bugs were
found.

\section{Conclusion}

Sprint 1 delivered a working, live-verified upload-to-extraction pipeline
for both CVs and TDRs, with a multi-provider LLM routing layer robust
enough to survive free-tier rate limits, quota exhaustion, and unreliable
structured-output generation: the foundation the matching and scoring work
in later sprints depends on. Beyond the original backlog, the sprint was
extended to make that pipeline trustworthy under real use: an asynchronous
processing path with live progress visibility for slow TDRs, a repeatable
extraction-quality eval harness to replace manual eyeballing, and a
hardened upload UX and finalized visual identity for the dashboard, all
confirmed against the running application (Section~\ref{sec:live-demo}).
The two open items (ADQ-8's gold-set annotation and ADQ-9's company data
request) carry forward, the latter now tracked as a set of explicit,
revisable working assumptions rather than a silent blocker.
